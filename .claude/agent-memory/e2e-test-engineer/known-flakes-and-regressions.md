## Resolved / fixed

- **`i18n/i18n.spec.ts` shard-4 failures — TWO distinct mechanisms, both root-caused from traces 2026-08-03 (`fix/e2e-flakes-promotion`, CI run 30790367863 shard 4, both blocking `E2E Gates` on promotion).** Prior memory entries had guessed "intermittent locale-init race" for both; only one of the two was interference.
  **`:305` "DELETE preference resets to system locale" (failed attempt AND retry) — self-inflicted, NOT cross-test interference.** Proof it needs no second test: the retry ran with zero concurrent i18n tests (previous test ended 06:35:46.466, retry began 06:35:56.679) and failed identically. Mechanism, read straight off `0-trace.network` joined against `0-trace.trace` call IDs: `setLanguage(page,'de')` PATCHes the server row AND writes `localStorage.locale='de'`, then leaves the page open. The test's `DELETE /api/users/me/preferences/locale` (204) lands while that page's `LocaleContext.syncWithServer` has a `GET /preferences` in flight; the GET is served **after** the delete commits, returns no `locale` row, so syncWithServer takes its else-branch — `readStoredPreference()` still reads `'de'` from localStorage → `upsertPreference('locale','de')` **re-creates the row the test just deleted**. Observed as an app-issued `PATCH /api/users/me/preferences` 13 ms after the DELETE on attempt 1 (`40.449Z` → `40.462Z`) and 18 ms after on the retry (`57.138Z` → `57.156Z`), with no corresponding test call anywhere in the trace's call list. The subsequent reload then reads `locale=de` and the page stays German — `error-context.md` shows `heading "Profil"`, `navigation "Hauptnavigation"`, `"Zeitplan"`. This is intended production behaviour (the localStorage→server migration path for pre-server-preference clients), so the app was not touched. The narrow ms-wide window is why it failed only sometimes (it passed on #1926).
  **Fix**: set German **server-side only** (inline PATCH, deliberately not `setLanguage()`), then `goto` + await the German `Profil` heading. That heading is the synchronisation point that proves syncWithServer took its _other_ branch ("server has a preference"), which applies the locale **and calls `localStorage.removeItem('locale')`** — so localStorage is provably empty before the DELETE, making the migration branch a guarded no-op (`if (localLocale !== 'system')` is false). No wait/timeout was added; the old `waitForLoadState('networkidle')` + `{timeout: 15000}` were **removed** (that timeout equalled the 15 s test timeout, so the assertion could only ever surface as an uninterpretable test timeout, never as an assertion failure).
  **`:131` "Key page headings render in German after language switch" (failed, passed on retry) — genuine cross-test interference on the shared admin's one `locale` row.** Timeline from the blob report: `:131` ran on worker 2 `06:35:34.182–43.650`; `:161` "Language can be switched back to English from German" ran concurrently on worker 1 `06:35:34.409–35.877` and PATCHes `locale='en'`. `:131`'s `Projekt` assertion passed at ≈`35.49`, then its `/schedule` load's prefs GET at `36.096Z` read `'en'`, and syncWithServer's server-authoritative branch applied English **and wiped `:131`'s own `localStorage.locale='de'`** — so it stayed English for the rest of the test. `error-context.md` confirms: `navigation "Main navigation"`, `link "Schedule"`.
  **Fix**: file-scoped `test.describe.configure({ mode: 'serial' })`. Must be file-scoped, not describe-scoped — the interference crossed describe boundaries (`:131` is in "Language Switching", and every one of the file's three describes PATCHes the same row via `setLanguage`/`resetToEnglish`).
  **Hardening added at coordinator's request** (worth repeating elsewhere): the fix above rests on an _inferred_ precondition ("localStorage is empty by the time the German heading renders"), which would silently stop holding if `test-results/.auth/admin.json` ever carried a `locale` entry — the page would then render German from localStorage before `listPreferences()` resolves, the heading assertion would pass early, and `removeItem` might not have run. Currently unreachable (`auth.setup.ts` only walks the setup form, and with no server preference yet neither syncWithServer branch writes localStorage), but the storage state is CI-generated and one flow change away. So the precondition is now **asserted, not inferred**: `await expect.poll(() => page.evaluate(() => localStorage.getItem('locale'))).toBeNull();` between the heading wait and the DELETE. `expect.poll` (not a bare `evaluate`) tolerates the removal landing a tick after the render without a fixed wait, and takes the project-default expect timeout — do not pass your own. Confirmed via `tsc` that `toBeNull()` is valid on the poll matcher type.
  **General lesson**: `LocaleContext.syncWithServer` makes the server row authoritative and _deletes_ the client's localStorage key when it applies a server value — so for locale tests the server row is the only real state, localStorage is not a private per-context override, and any other writer to that row (same file or another) hijacks the test. Also: when both an attempt and its retry fail but the retry ran alone, cross-test interference is ruled out by construction — look for the app issuing its own requests (join `before`/`after` trace events by `callId` and diff the network log against the test's own call list; a request in `trace.network` with no matching call is the app).

- **`dashboard.spec.ts` Scenario 6/7 (dismiss/re-enable) — root cause finally found and fixed 2026-08-03 (`fix/e2e-flakes-promotion`)**, ending a recurrence that had been mis-diagnosed/re-patched at least 3 times since #1431 (PR #1445 `expect.poll`; flagged again but left untouched in PR #1883 shard 5; hard-failed attempt+retry in PR #1935 shard 6 as `:516` "Dismissed card stays hidden after page reload"; also implicated `:492` and `:566`). **Actual root cause**: `dashboard.hiddenCards` is a single preference row keyed by userId, and every test in `dashboard.spec.ts` (like nearly every E2E test in this suite) authenticates as the ONE shared admin user (`test-results/.auth/admin.json`). `playwright.config.ts` runs `fullyParallel: true`, so the ~30 unrelated tests in this file — every one of which runs the file's top-level `beforeEach` that PATCHes `dashboard.hiddenCards` back to `"[]"` on that same shared admin user — can be scheduled onto a different worker and land their reset in the narrow window between a dismiss-test's own dismiss-PATCH and its post-reload GET, wiping out the exact state under test. Confirmed the write/read path itself is NOT buggy: `upsertPreference()` writes synchronously via better-sqlite3 and returns before the route handler sends its 200, `DashboardPage.dismissCard()` already awaits that PATCH response before returning, and `handleDismissCard()` in `DashboardPage.tsx` awaits `upsertPreference()` before ever updating local state — so by the time the card visually detaches, the server write is already durably committed. All three previous "fixes" (`expect.poll`, `waitForResponse`, `test.describe.configure({mode:'serial'})` scoped to just the 2 tests in Scenario 6) were synchronization band-aids on a single describe block; none of them — nor could any of them — stop a DIFFERENT describe block in the same file (or a different worker entirely) from concurrently mutating the same shared-admin preference row, since `mode:'serial'` only serializes tests _within_ the configured block.
  **Fix (test-only, `e2e/tests/navigation/dashboard.spec.ts`)**: gave all 4 preference-mutating tests (Scenario 6's 2 dismiss tests + Scenario 7's 2 re-enable tests) their own dedicated user + fresh browser context via a new `loginAsIsolatedDashboardUser()` helper, mirroring the established pattern already used in `e2e/tests/i18n/i18n-categories.spec.ts` and `e2e/tests/profile/change-password.spec.ts` (`createLocalUserViaApi` + `browser.newContext({storageState:{cookies:[],origins:[]}})` + `POST /api/auth/login`). A dedicated user's `dashboard.hiddenCards` row can never be touched by any other concurrently running test. `user_preferences.user_id` has `ON DELETE CASCADE` (see `0018_user_preferences.sql`), so `deleteUserViaApi()` in each test's `finally` block cleans up the preference row too — the old manual "PATCH hiddenCards back to `[]`" cleanup calls were removed as no longer needed. Removed the now-unnecessary `mode: 'serial'` on Scenario 6 (each test is now fully self-contained). The file's top-level `beforeEach` (admin-user preference reset) was left untouched — it still protects the other ~26 admin-page tests in this file.
  **General lesson**: any preference/setting that is stored per-USER rather than per-entity is invisible to the `testPrefix` per-worker-naming convention (which only namespaces entity names) and is NOT safe to mutate on the shared admin user under `fullyParallel: true`, no matter how carefully a single describe block is internally serialized — the only reliable fix is a dedicated user (or dedicated context/session) per test, not tighter waits. Grep for other tests that PATCH/DELETE `/api/users/me/preferences` on the plain `page`/`authenticatedPage` fixture (shared admin) rather than a scoped/dedicated user before assuming a similar test is race-free.

- **`invoices.spec.ts:841` "Effective Amount"/"Remaining Amount" column toggle — actual root cause found 2026-08-03 (`fix/e2e-flakes-promotion`), after TWO prior wrong diagnoses on the same test.** Recurred identically on every beta PR from #1880 onward (nine consecutive PRs, shard 5, both attempt+retry, every single time) — this framing ("since #1880") was itself the tell in hindsight: #1880 is the exact commit that introduced `getColumnCellText()`, so the test had never once passed, not "started flaking."
  **Wrong diagnosis #1** (this file, superseded): theorized an `enableColumn()`-ordering race in `useColumnPreferences`'s debounce/re-sync — real hazard, real fix, but NOT what was failing this test. Root-cause fix shipped (`enableColumn()` now awaits its own `PATCH /api/users/me/preferences` before returning) and the test still failed identically on the next CI run.
  **Wrong diagnosis #2** (proposed, never shipped): shared-admin-user preference-row contamination, by analogy to the `dashboard.spec.ts` fix below (same file, same day). Investigated with a full trace/network timeline before touching code: pulled `1-trace.network` from the failing run's artifact and confirmed the two `enableColumn()` PATCHes were clean, sequential, non-overlapping (823ms apart, no interleaving) — ruling out both the ordering race AND cross-test interference as the actual mechanism for THIS test. Also confirmed structurally that no other page/test uses the `table.invoices.columns` preference key (`pageKey="invoices"` is unique to `InvoicesPage.tsx`), so there was no plausible writer to contaminate the row even in principle.
  **Actual root cause**: `.tableHeader` (`DataTable.module.css`, present since the DataTable component's introduction in PR #1102, months before this test existed) applies `text-transform: uppercase` to every `<th>`. `innerText()` returns the browser's _rendered_ text — reflecting that CSS transform — so `headers.nth(i).innerText()` returns `"REMAINING AMOUNT"`, never `"Remaining Amount"`. `getColumnCellText()`'s case-sensitive `text === columnLabel || text.startsWith(...)` comparison against the mixed-case label passed by the test therefore can never match, for any column, deterministically — not a timing issue at all. Proved this directly from the trace: pulled `1-trace.trace` from the same artifact and joined `before`/`after` events by `callId` to read the actual `innerText()` return values recorded during the failing test's `toPass()` retry loop — every single header-scan iteration across the full 3-second window returned the same uppercase string (`'REMAINING AMOUNT'`, `'EFFECTIVE AMOUNT'`, etc. — all ten headers, every pass), with zero variation. That directly falsifies "transient absence that self-heals": there was no healthy state to revert from or heal back to. The `error-context.md` snapshot showing the column "present" at throw time (which both prior diagnoses read as evidence of a race) is the ARIA-computed accessible name, a completely different code path that `text-transform` does not affect — it was never in tension with the innerText mismatch, just adjacent to it.
  **Fix (test-only, `e2e/pages/InvoicesPage.ts`)**: `getColumnCellText()` now upper-cases both the header's `innerText()` and the expected `columnLabel` before comparing. Preserves the existing exact/prefix-match discriminating logic (still distinguishes e.g. "Amount" from "Remaining Amount") — just makes it correctly account for the deliberate, long-standing visual uppercase transform, the same way a human reading the UI would. Kept the `enableColumn()` `waitForResponse()` fix from the wrong-diagnosis-#1 round — it closes a real, separately-filed production hazard (#1955) and is harmless — and kept `getColumnCellText`'s `toPass({timeout:3_000})` retry as a defensive backstop, but neither is "the fix" for this test; the case-insensitive comparison is.
  **General lesson**: when a header/label-matching helper reads `innerText()` (not `textContent()`) against an expected string literal, check the element's computed `text-transform` before trusting a case-sensitive comparison — `innerText()` reflects CSS transforms, `textContent()` does not, and a mismatch here is 100% deterministic (fails on literally every run) rather than intermittent. When a "flaky" test is actually failing on _every_ run with no exceptions, prefer that explanation over a race theory — pull the actual `innerText()`/network values from a trace before proposing a second timing fix. `getColumnCellText()` is currently only used by this one test; if a future test reuses it against a differently-styled table, this same case-normalization already covers it.
  **Second latent bug, uncovered once the header-scan fix let the test run past line 930 for the first time**: the row read itself (`getColumnCellText(invoiceNumber, ...)` → `row.locator('td').nth(columnIndex)`) assumed the test's own invoice would be on page 1 of the unfiltered list after `invoicesPage.goto()`. The invoice is created with a fixed `date: '2026-01-01'`; with `pageSize=25` and every worker creating invoices concurrently for the whole CI run, an invoice that old is easily pushed past page 1 (confirmed via the failing run's `error-context.md`: `"Showing 1–25 of 37 items"`, and the invoice number string absent from the snapshot entirely). This is the **exact same bug shape already fixed once before in this file** — see the `invoices.spec.ts:395` entry a few lines up (PR #1883 point 2) — but it recurred here because this test's row-read (inside `getColumnCellText`) had never once executed before either of the two `getColumnCellText` fixes above, so it was never exercised in CI. **Fix (test-only, `e2e/tests/invoices/invoices.spec.ts`)**: added an `invoicesPage.search(invoiceNumber)` call (same `?q=` server-side `invoiceNumber` LIKE-match navigation as the `:395` fix) between the "toggle columns on the unfiltered list" section and the two `getColumnCellText()` calls, narrowing to exactly this test's own row before reading cells. Since `table.invoices.columns` is a server-persisted preference, it survives the full `page.goto()` `search()` does — verified rather than assumed, by re-asserting both `columnheader` locators are still visible on the freshly re-mounted, filtered page before reading cells off it. Also added a positive-control `expect(page.getByRole('columnheader', {name: 'Invoice #'})).toBeVisible()` before the two pre-toggle `not.toBeVisible()` checks, since a `getByRole` locator matching zero elements passes `not.toBeVisible()` vacuously — the positive control proves the table actually rendered, so the negative checks are meaningful.
  **Arithmetic re-verified against current production code** (not just trusted from the test's own comments), since these assertions were also running for the first time: `remainingAmount = invoice.amount − Σ budgetLines[].itemizedAmount` (`invoiceBudgetLineService.ts`, several call sites, all consistent) gives `1000 − 300 = 700`; `computeFinalPaymentAmount()` (`depositAggregateUtils.ts`, current post-#1922-claim/deposit-split version) gives `max(0, invoiceAmount − depositSum − receivedRefundSum) = max(0, 1000 − 0 − 150) = 850` since the test's one deposit entry is `entryType: 'refund'` at `status: 'paid'` by read time. Confirmed the list endpoint (`invoiceService.ts` `listAllInvoices`) populates `budgetLines` with real per-invoice data (only `deposits` is stubbed `[]` for list rows, per its own comment — `finalPaymentAmount` is separately bulk-computed and unaffected). Both expected values (700, 850) were correct; nothing needed changing.
